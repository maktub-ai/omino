# Omino v0 开发文档

日期：2026-11-17。状态：**v0 已按本文实施**，所有自动验收（A1–A7）通过；第 7 节的人工评测待用真实 agent 运行。本文是 v0 的范围、格式、命令与验收标准；与 `HANDOFF.md` 的产品意图冲突时，以 HANDOFF 和用户后续表达为准。

## 1. 一句话

Omino 是一份**写给 agent、也让人看得懂的项目计划笔记**：保存在被管理项目的 `.omino/` 目录里，由一个 skill 告诉 agent 每轮怎么读、怎么写，由一个零依赖脚本做确定性的校验和计算，由一个静态页面让人阅读。它不是 agent，也不执行任务。

名字来自 polyomino / tetromino 的词根 *-omino*：由一个个方格拼成的形状。每篇笔记是一块，阶段、工作线和关系把它们拼成一张图。

## 2. v0 范围

**做：**

1. `.omino/` 文件格式（第 4 节）。
2. `SKILL.md` 与 `references/`：每轮的读、写、保持、召回、复核行为（第 6 节）。
3. 脚本 `omino`：`init`、`record`、`check`、`recall`、`review`、`view` 六个命令（第 5 节）。
4. 静态阅读页：沿用正式版 demo 的界面，数据内联，离线可开。
5. 测试：脚本的自动测试，以及 agent 行为的人工评测清单（第 7 节）。

**不做：** hook 与自动注入、多 agent 并发写入、界面上的编辑或裁决按钮、看板与列表视图、npm 发布、许可证与远端仓库（另行决定）。

**约束：** 只用 Node 内置模块（Node ≥ 18），不引入任何依赖；全部示例数据为虚构的 Todo App；不读取、不引用 Mandala 的代码或数据，只沿用其视觉 token 的色值。

## 3. 核心语义

| 概念 | v0 的表达 |
|---|---|
| 意图 | `project.md`：目的、原则、边界；以及每篇笔记里“为什么”的正文 |
| 安排 | 阶段（`stage`）、工作线（`lane`）、阶段内顺序（`order`）、安排先后（`before`） |
| 进展 | 状态（`status`）+ 来源（`source`），每次变化写入 `changes.jsonl` |

**四种关系，互不冒充：**

| 关系 | 字段 | 含义 | 会不会阻塞 |
|---|---|---|---|
| 归属 | `stage`（以及可选的 `parent`） | 属于哪个阶段、服务哪个目标 | 否 |
| 执行前置 | `requires: [id]` | 这些完成后，本项才有条件开始 | 是，用于推算“等待前置” |
| 安排先后 | `before: [id]` | 人希望本项排在它们前面；不是技术依赖 | 否 |
| 上下文 | `refs: [id]` | 相关的决定、约束、理由 | 否 |

`requires` 必须无环；`before` 和 `refs` 不检查环。没有记录 `requires` 不等于可以安全并行，界面和 agent 都不得把它说成“已确认可并行”。

**状态只存“人或证据给出的事实”，推导出来的东西不存：**

- 工作项 `status`：`planned | doing | done | verified | dropped`。`verified` 只能来自 `source: tool`。
- “等待前置”是推导的：`planned` 且有未完成的 `requires`。
- “需复核”是推导的：完成依据漂移，或笔记带有 `review` 标记（第 5.5 节）。
- 阶段 `status`：`planned | active | closed`。
- 想法：`idea_state: open | deferred | adopted | dropped`，召回另存 `recall_state: waiting | fired | stopped`。

**来源（`source`）：** `user`（用户在对话里说的）、`agent`（agent 自报）、`tool`（测试或命令的结果）、`file`（有人直接改了文件，事后由 `check --fix` 补记）。

## 4. 文件格式

```
.omino/
├── project.md          # 意图，kind: intent，id 固定为 project
├── stages/<id>.md
├── work/<id>.md
├── ideas/<id>.md
├── changes.jsonl       # 只追加的变化记录
├── state.json          # 每篇笔记最后一次被记录时的指纹，用来发现未记录的修改
└── view.html           # 由 view 生成，可加入 .gitignore
```

每篇笔记是 Markdown，开头一段 frontmatter。为保持零依赖，frontmatter 只支持一个**严格子集**：每行 `key: value`；值是字符串、整数，或行内列表 `[a, b]`；不支持嵌套、多行值和注释。

```markdown
---
id: filter
kind: work
title: 只看未完成
stage: s1
lane: view
order: 2
status: done
source: user
before: [del]
---

## Why
只看还没做完的待办，让当天剩下的事一目了然。

## Requirements
- 列表可以切换为只显示未完成的待办。

## Arrangement
用户说“这个先做”，在第一阶段内排在删除之前。

## Progress
用户在第 6 轮报告已做好并检查过。
```

字段表：

| 字段 | 适用 | 必填 | 说明 |
|---|---|---|---|
| `id` | 全部 | 是 | `[a-z0-9-]+`，全局唯一，与文件名一致 |
| `kind` | 全部 | 是 | `intent | stage | work | idea` |
| `title` | 全部 | 是 | 一行标题 |
| `level` | stage | 是 | 整数，推进阶段的先后（1、2、3…） |
| `stage` | work | 是 | 所属阶段 id |
| `lane` | work | 否 | 工作线名称；缺省为“未分组” |
| `order` | work | 否 | 阶段内展示顺序 |
| `status` | work、stage | 是 | 见第 3 节 |
| `source` | work、stage | 否 | 最近一次状态变化的来源 |
| `requires`、`before`、`refs` | work | 否 | id 列表 |
| `parent` | work | 否 | 目标拆解时的上级工作项 |
| `idea_state` | idea | 是 | `open | deferred | adopted | dropped` |
| `recall` | idea | 否 | 召回条件，见第 5.4 节 |
| `recall_state` | idea | 有 `recall` 时必填 | `waiting | fired | stopped` |
| `basis` | work | 由脚本写 | 完成时 Requirements 的指纹，不要手改 |
| `review` | work、stage | 否 | 一句话原因；agent 判断出语义冲突或需复核时写入 |

正文用英文二级标题分节（`Why`、`Requirements`、`Arrangement`、`Progress`，可自由增加），内容用项目所用的语言。**`Requirements` 一节是复核的依据**：完成后它变了，就视为需要复核。

`changes.jsonl` 每行一条：

```json
{"ts":"2026-11-17T09:02:00Z","source":"user","summary":"加入筛选，排在删除之前","notes":[{"id":"filter","op":"created"},{"id":"del","op":"modified"},{"id":"s1","op":"modified"}]}
```

## 5. 命令

调用方式：`node <skill 目录>/scripts/omino.mjs <命令> [参数]`。默认在当前目录寻找 `.omino/`；`--dir <path>` 可指定。所有命令支持 `--json`，输出给 agent 解析；否则输出给人读的简短文本。退出码：0 正常，1 发现需要处理的问题，2 用法或格式错误。

### 5.1 `init`

创建 `.omino/`、`project.md` 模板（只有目的、原则、边界三个空节）和空的 `changes.jsonl`、`state.json`。已存在时拒绝执行。**不创建任何阶段或工作项**。

### 5.1a `init --adopt`（实施时补充：接入已有项目）

用于已经开发了一段时间的项目。除 `project.md` 外，还生成 `stages/s0.md`：标题 “Before Omino”，`level: 0`，`status: closed`，`source: agent`，正文只写现有能力的摘要和依据。`project.md` 带 `review` 标记，表示这是 agent 根据 README 等文档起草的推测，用户确认后才去掉。

规则：不为过去的功能补建完成记录（没有可复核的要求）；已有的 TODO、issues 只有在用户同意时才导入，且只作为未安排的想法；之后按讨论涉及的范围逐步增加笔记，不一次性扫描整个仓库。对应自动测试 A8，人工评测 C1–C4。

## v0.6（2026-11-20）：一个常驻的页面服务，页面上能直接改

v0.5 的 live 模式要 agent 在后台 `poll` 才能收到页面上的点击；没人在听时，页面显示“已发送，等待 agent 处理”，看起来像坏了。实际用下来，在 Claude / Codex 客户端里引用页面内容发给 agent 就够了，“页面叫醒 agent”是伪需求；真正缺的是用户自己能在页面上改。

- **去掉 live 模式**：`live`、`poll`、`reply`、`inbox`、`stop`、`serve` 和 `/omino:live` 都删了；每份计划各自的页面服务（`.serve.json`、`.live.json`）也删了。
- **一个页面服务管本机所有计划**：固定端口 4870（`OMINO_PORT`），`/p/<id>` 是每份计划的页面，`/` 是总览。会话开始的 hook 拉起它，之后一直运行；`omino service install` 让它开机登录后自动启动（macOS 用 launchd，Linux 用 XDG autostart，Windows 用启动文件夹里的脚本），由 agent 问用户一次。旧版本的服务会被新版本替换，新版本的不会被旧版本替换。
- **页面上直接改**：每篇笔记有“编辑”，改的是带 frontmatter 的 Markdown 原文。保存时：id 和类型不能改；改完计划必须仍然有效，否则不写入；打开编辑之后文件被别人改过就提示冲突，可以覆盖或载入最新。保存即记录，来源是用户（`via: page`），只记这一篇——agent 还没记录的改动不会被算到用户头上。
- **确认当场生效**：待确认的草稿、agent 报告的完成、要求变了的已完成工作，在页面上点“确认无误”就直接记作用户确认。
- **回答、质疑、留言都是留言**：写进笔记的 `## Comments`，格式是 `> [!omino] 标签` 加正文。单独一节，所以不会动到 Requirements、不会让已完成的工作显示为“需复核”。agent 在用户下一条消息时看到（hook），照着改计划，再把这段删掉。
- **安全**：只监听 127.0.0.1，检查 Host（防 DNS rebinding）；页面不需要令牌，`/api/` 下的读写都需要 `~/.omino/token`。其他应用（Mandala tab）从 `~/.omino/server.json` 读端口和令牌。
- **静态页**：`view.html` 只读，打开时探测页面服务，在就给出“在本地页面中打开（可编辑）”的链接。
- **兼容**：0.5 留在 `inbox.jsonl` 里没处理的回答，hook 会转成留言，文件改名为 `inbox.migrated.jsonl`。

## v0.5.1（2026-11-19）：一份计划管什么

按「情况分类」（见 docs/framework.md）补齐：
- 「项目意图」改叫「目标」；SKILL 写清自己的产品、老仓库里的一件事、fork 三种情况下目标怎么写，以及划分规则（目标相同就是同一份计划；并行放泳道，先后放阶段）。
- `init --name <id>`：按这份计划要做的事起名。
- 关联默认只记在本机（`.git` 里的 `omino-project`），`--share` 才写 `.omino.json`；团队仓库和 fork 不往仓库里加文件。`setup` 不再写 `.omino.json`。
- `omino lane "<名字>"`：泳道 ↔ 仓库对应，记在计划的 `omino.json`；简报说明当前目录在哪条泳道，没有时让 agent 问一次；泳道图在泳道名下显示对应仓库。
- 在 git 仓库里往上找配置时越过仓库根目录，认到工作区父目录（Codex project、多目录工作区）的 `.omino.json`；仓库自己有计划时优先。
- `omino close [--reopen]`：计划结束后只读，`record` 拒绝修改，简报提示；同一目录用 `init --name` 开下一份计划，旧的仍在 `projects` 里。
- 写入加锁：`record`、`link`、`lane`、`close` 在计划目录里建一个 `.lock` 目录（原子操作）后才写，后来的进程排队等，最多 10 秒；锁的主人进程不在了（崩溃）就自动接管，不会把计划永久锁死。`.lock` 不进计划历史。不需要常驻服务。
- `omino projects --open`：本机所有计划的总览页（目标、进度条、当前阶段、待决定数、仓库），点进各自的计划页。

## v0.5.0（2026-11-18）：计划移出工作目录

起因：Mandala 用一个任务一个 worktree 的方式开发，计划放在仓库的 `.omino/` 里会带来三个问题：并行任务各改一份计划，合并时冲突；某个 worktree 里的更新在合并前其他地方都看不到；agent 读到的可能是自己分支上的旧计划。参考 engram（主存储是全局的 SQLite，项目身份记在 git 共享元数据里，仓库里只放导出物），改成：

- 计划放在 `~/.omino/projects/<id>/`（可用 `OMINO_HOME` 改位置），格式不变，仍然是 Markdown。同一台机器上同一个项目的所有 worktree 和 clone 共用这一份。
- 项目 id 的来源：先看项目目录里的 `.omino.json`（`{"project": "<id>"}`，git 以外的目录 `init` 会写它）；没有的话，看 git common dir 里的 `omino-project`（`init` 写入，linked worktree 共用，不进版本库）。新 id 取 origin 的 `owner-repo`，所以别的 clone `init` 时会接上同一份计划；没有 remote 时用目录名，并保证不重名。
- 计划目录本身是 git 仓库：`init`、`migrate`、每次 `record` 各提交一次，计划有完整历史，又不混进项目的提交。不再要求「计划改动和代码一起提交」。
- 新命令：`where`（输出计划目录）、`migrate`（把仓库里的旧 `.omino/` 复制过去；旧目录由用户决定删除）、`allow`（把计划目录加进 Claude Code 的 `additionalDirectories` 和 Codex 的 `writable_roots`，只在用户同意时运行）。`doctor` 会检查这几项。
- 笔记里链接到项目文件时，写成以 `/` 开头的项目相对路径；旧写法 `../src/x` 仍按项目目录解析。live 页面的 `/file?f=` 读项目文件，`/file?p=` 读计划目录里的文件。
- 旧计划在会话开始时会收到提示，agent 问用户一次要不要迁移；没迁移之前，命令都会提示先跑 `migrate`。

项目和计划的关联（参考 engram：项目由目录现场判断、认不准就报错、每个回答都写明项目）：

- 三层关联各记一处：项目 → 计划 id 记在仓库里提交的 `.omino.json`；计划 id → 本机目录；计划 → 所属仓库记在计划目录的 `omino.json`。以后的云同步只是计划的第三层多一个同步目标，仓库不用改。
- `init`、`migrate` 写 `.omino.json`，同时在 git common dir 写绑定，在提交前创建的 worktree 也能找到计划。`.omino.json` 格式不对直接报错，不退回猜测。
- 目录的 remote 不在计划的 `repos` 里（fork、remote 改名、复制来的 `.omino.json`）时，简报、`where`、`doctor` 都会提示，agent 改计划前先问用户；`omino link <id>` 由用户确认后改绑，并加入这个 remote。
- 一份计划可以对应多个仓库（都 link 到同一个 id）；monorepo 的子目录可以有自己的 `.omino.json`，按最近的那个认。一个目录同时写多份计划不支持。
- `omino projects` 列出本机所有计划、所属仓库和用过它的目录；所有 `--json` 输出开头都有 `project: {id, via, root}`；`record` 的输出写明计划 id。

用户只用对话：本机需要的设置（迁出旧计划或从 git 历史恢复、写 `.omino.json`、`allow`、更新 `~/.codex/skills/omino` 等旧的技能副本）合成一个 `omino setup`。会话开场的 hook 发现需要设置时，列出会改的内容，让 agent 问用户一次，同意后 agent 自己运行；`--dry-run` 只列出步骤。SKILL 明确：不让用户在终端里跑任何命令。

hook 对 Claude Code 和 Codex 通用：两者的 hook 格式和输入字段相同，Codex 运行插件 hook 时也设置 `CLAUDE_PLUGIN_ROOT`。仓库加了 `.codex-plugin/plugin.json`，默认读 `hooks/hooks.json`；不装插件时，`setup` 把 hook 写进 `~/.codex/hooks.json`（用户级，所有项目通用，命令里补上 Homebrew 的 PATH），用户在 Codex 里用 `/hooks` 批准一次。`omino brief` 本身也带上一次性设置的提示，只靠 AGENTS.md 的 agent 读计划时同样会来问。`doctor` 分别检查两个 agent 的 hook，发现重复配置会提示。

代价：计划不再和代码在同一个 PR 里 review；切到旧 commit 时看不到当时的计划，要看计划目录的历史。跨机器和多人同步留到 v0.6，同步单位用 `changes.jsonl` 里只追加的事件。

## v0.4.1（2026-11-18）：按行为评测修正

用较弱的模型（Haiku）扮演 agent，在空的记账项目里按 13 步真实地走了三次会话（hook 用真实脚本触发），找出不自然的地方后修正，再跑一遍对比。修正：

- 只有用户用 `/omino:plan` 或明确要计划时才建 `.omino/`，否则只问一次；意图只写用户说过的话。
- 用户说的安排（“第一版做 A、B、C，C 最后”）直接写成阶段和工作项，不算推断；在此之上补充的细节才是草稿，要标待确认。写下计划不等于开工，记录后先问要不要开始。
- “先不急”“以后再说”这类针对已有事项的话，写进该事项的安排说明；`brief` 新增“Next in the plan”，带上这些说明，新会话说“继续”时不会直接开做。
- 同一轮改了已完成事项的要求、实现并通过测试时，用测试结果确认；`record` 会提示这类事项和确认命令。
- 计划的改动和代码一起提交，不单独提交。
- 每轮结束的提醒只在有实质改动（新增文件或约 20 行以上）时触发，措辞改为“多数改动不需要动计划”；同时修复了未跟踪文件的改动检测不到的问题。
- 暂缓（deferred）的想法如果带召回条件，到期也会召回。
- 新增插件命令 `/omino:plan`。

## v0.4（2026-11-17）：本地闭环

定位和整体结构见 `docs/framework.md`。本版目标是让计划不断档，全部在本地完成，不做常驻服务和任何线上部分。

- **Claude Code 插件**：仓库根目录即插件和插件市场（`.claude-plugin/plugin.json`、`marketplace.json`），插件包含 skill 和 `hooks/hooks.json`。安装：`/plugin install omino --marketplace maktub-ai/omino`。
- **hook**（`omino hook <事件>`，从 stdin 读 Claude Code 的输入；没有 `.omino/` 时什么都不做；出错也不影响会话）：
  - `session-start`：输出 `omino brief` 作为上下文，并在后台启动本会话的页面服务（`.serve.json` 记下会话 id）；
  - `prompt`：把 inbox 里本会话还没提过的回答带给 agent，同时记下这一轮开始时工作区的指纹；
  - `stop`：这一轮工作区（`.omino/` 以外）有变化、`changes.jsonl` 却没变时，返回一次 `decision: block` 提醒 agent 检查是否要记录；`stop_hook_active` 时不再提醒；
  - `session-end`：停掉本会话启动的页面服务。
  - 各会话的状态在 `.omino/.hooks.json`（git 忽略，7 天后清理）。
- **`omino hooks install|remove|status [--scope project|user]`**：不用插件时，把同样的 hook 写进 `.claude/settings.json`，保留已有的其他 hook，可重复执行。
- **`omino doctor`**：检查 Node、格式版本、笔记错误、`.gitignore`、hook、AGENTS.md 提示，只报告和建议，不修改。
- **`omino brief`**：会话开始的十行左右简报。
- **`omino find <关键词>`**：按标题、id 和正文打分搜索；skill 要求新建笔记前先搜。
- **孤立笔记**：没有任何关系进出的想法和决定，`check` 给出警告，`record` 在新建时提示。决定的 `affects` 可以指向 `project`，表示关于整个项目的决定。
- **格式版本**：`state.json` 的 `version` 即文件格式版本（当前 1）。遇到更新的格式，`record` 拒绝写入，`check` 报错，hook 只提示更新。
- **决定指向整个项目**：`affects: [project]` 只是建立关联，不会把意图标为待复核；同一个目标也不会被重复列出。
- **关系图改版**：意图、最近的决定（最新 3 个）、未安排的想法（到期的在前，最多 3 个）移到画布上方，成为三张固定宽度的卡片，不随画布变宽、不随画布横向滚动；泳道图只放阶段和工作。选中一个决定或想法时，它影响、取代或等待的工作在泳道图里高亮，其余变淡；选中一个工作时，指向它的决定和想法在上方高亮。已结束的阶段默认折叠成一条窄列，点击展开，选择保存在浏览器里；深链接到已结束阶段里的笔记时自动展开。
- **一条命令进入 live 模式**：`omino live [--open]` 在后台启动页面服务（或复用会话开始时 hook 启动的那个）并打开页面；插件提供 `/omino:live` 命令。agent 把 `omino poll` 作为后台任务运行，页面上一点击就能收到，像 Impeccable 的 live 模式一样，但不占住对话。被 poll 取走的事件在 inbox 里记一条 `delivered`，发消息时的 hook 不再重复交给 agent。页面服务在运行时，`record` 和 `view --open` 给出的链接指向实时页面而不是静态文件。对应测试 A15。
- **其他**：任何命令加 `--help` 只打印帮助（修复 `init --help` 会创建 `.omino/` 的问题）；阅读页“需要你决定”不再计入“等待前置”；深链接只做最小滚动，不把左侧的意图和阶段滚出视野。
- 许可证定为 MIT。

对应自动测试 A14。试用计划：better-plan 仓库的 `.omino/` 用 Omino 管理 Omino 本身，每完成一部分就用新版本更新。

## v0.3（2026-11-17）：在页面上回答（live 模式）

参考 impeccable 的 live 模式：`omino serve` 在 127.0.0.1 上提供阅读页（一次性令牌 + Host 校验），页面上可以回答 Open questions、确认或指出需复核项有问题、对召回的想法选择采纳 / 暂缓 / 放弃、对任一笔记留言。页面只把这些写进 `.omino/inbox.jsonl`（只追加、git 忽略），从不修改计划。agent 在后台循环 `omino poll`（最长阻塞 10 分钟，返回 event / timeout / exit / offline），像对待对话消息一样处理，改笔记并用 `--said` 记下原话，再 `omino reply <id> --message` 回执；页面通过 SSE 收到回执后刷新并显示 agent 的说明。没人轮询时提交的回答会在下次 `check` / `review` 中列出。`omino stop` 结束服务；空闲两小时自动退出。限制：agent 与浏览器需在同一台机器上。对应自动测试 A12。

## v0.2（2026-11-17）：决定与追溯

**决定（decision）**：新增 `decisions/<id>.md`，字段 `date`（必填）、`source`、`supersedes`、`affects`，正文 `Before` / `Now` / `Why` / `Given up`。被取代的笔记保留，显示为“已被取代”，不再进入“需要你决定”。`record` 发现新增或修改的决定时，对 `affects` 中已经在做或已完成、且这次没有一起修改的笔记自动写上 `review`；同一步里一起改过的视为已经有意调整，不再标记。SKILL.md 规定：方向改变时先写决定再改安排；开会话时先读最近的决定；用户提出已被否决的方案时指出对应的决定。

**追溯**：每条变化记录自动带上 git 分支、提交和（链接工作树时的）worktree 名；`--session` 或环境变量 `OMINO_SESSION` 记录会话 id；工作项新增 `branch` 字段。设置 `OMINO_NO_GIT` 可关闭 git 采集（示例数据生成时使用）。

**阅读页**：意图下方增加“决定”一行；被取代的节点淡化并加删除线；关系里显示“取代 / 被它取代 / 影响 / 受它影响”；历史条目显示分支@提交、worktree、会话。

### 5.6g 静态页也能回答（2026-11-17）

静态页（`view` 生成的 view.html）原来只有一行提示，用户找不到回答的地方。现在静态页和实时模式一样，在每个待回答的问题、待确认的草稿、到期的想法和评论处都有输入框；按钮是“复制”，把回答整理成一段带笔记标题和路径的话复制到剪贴板，用户粘到对话里交给 agent。实时模式下按钮仍是“发送”。SKILL.md 补充：页面上有待回答的问题、且 agent 在用户本机运行时，优先用 `serve --open` 打开。

### 5.6f 正文 Markdown 渲染（2026-11-17）

笔记正文按常用 Markdown 渲染：标题、引用、表格、有序/无序/嵌套列表、任务项、代码块、行内代码、粗体/斜体/删除线、链接、图片，HTML 注释不显示。常见小节标题（Requirements、Open questions 等）在中文界面下显示中文。正文排版加大行距、标题用正文色。链接：指向另一篇笔记的相对路径在侧栏打开那篇笔记；指向仓库里其他文件时，静态页用相对 `.omino/` 的路径，实时模式经只读路由 `/file`（限项目目录内、拒绝 `.git` 与 inbox/serve 文件、2 MB 上限、沙箱 CSP）。对应测试 A13。

### 5.6e 笔记属性收成一行（2026-11-17）

右侧笔记的属性（状态、阶段、工作线、来源、分支等）从两列卡片改为标题下的一行小字；需复核、待确认、等待前置等改为小标签，原因放在悬停提示里；待回答的问题不再单独成块，正文里的 `Open questions` 小节以提示色标出，标签点击可跳过去。正文是重点。SKILL.md 补充：开会话时若有待回答的问题或待确认的草稿，在对话里简短问一次。

### 5.6d 变化在对话里确认（2026-11-17）

阅读页在关系图之外增加看板（按显示状态分列）和列表（按阶段分组的表格），与筛选、笔记面板共用同一份数据，只读，视图选择保存在浏览器本地。

### 5.2 `record "<一句话>" --source user|agent|tool|file [--confirm id,id]`

1. 对比每篇笔记当前的指纹与 `state.json`，得出新建、修改、删除的笔记。
2. 没有任何变化时只提示“没有可记录的变化”，不写记录，退出码 0。
3. 对状态刚变成 `done` 或 `verified` 的工作项，写入 `basis`（Requirements 的指纹）。
4. 校验 `verified` 只能配 `source: tool`。
5. 追加一条 `changes.jsonl`，更新 `state.json`。
6. `--confirm <id>`：用户确认某个需复核的完成仍然成立时使用，按当前要求重新写入 `basis`（实施时补充）。

### 5.3 `check [--fix]`

校验格式与引用：必填字段、枚举值、id 唯一且与文件名一致、`stage`/`requires`/`before`/`refs`/`parent` 指向存在的笔记、`requires` 无环、frontmatter 只用子集语法。

另外发现**未记录的修改**（指纹与 `state.json` 不符却没有对应记录）。带 `--fix` 时，以 `source: file`、说明“文件被直接修改”补一条记录；格式错误不自动修。

### 5.4 `recall [--mark-fired <id>] [--stop <id>]`

列出 `recall_state: waiting` 且条件已成立的想法。v0 支持的条件：

| 写法 | 成立条件 |
|---|---|
| `stage <id> closed` | 该阶段 `status: closed` |
| `work <id> done` | 该工作项为 `done` 或 `verified` |
| `manual <说明>` | 脚本无法判断，单独列为“需要你判断”，并注明未自动核验 |

agent 把想法带回讨论后，调用 `--mark-fired` 设为 `fired`；用户决定暂缓或取消后，agent 把 `idea_state` 改为 `deferred`/`dropped`，并调用 `--stop` 设为 `stopped`。`fired` 和 `stopped` 都不会再次出现在列表里。这就是“召回不等于采纳”和“讨论过的事不反复提醒”的机制。

### 5.5 `review`

输出“需要你决定”列表，全部由当前状态推导：

| 类别 | 判定 |
|---|---|
| 依据已变 | `done`/`verified` 且当前 Requirements 指纹 ≠ `basis`；或它的某个 `requires` 在本项完成后又被修改 |
| 标记复核 | 笔记带有 `review` 字段（包括与意图冲突） |
| 待确认完成 | `status: done` 且 `source: agent` |
| 等待前置 | `planned` 且有未完成的 `requires` |
| 已召回待讨论 | `recall_state: fired` 且 `idea_state: open` |

复核只指出，不重置：旧的完成记录保留，由人确认后，agent 用 `record --confirm <id>` 更新 `basis`。

### 5.6 `view [--out <file>]`

读取全部笔记、推导状态与关系，生成单个 HTML（数据内联，`file://` 可直接打开），默认写到 `.omino/view.html`。界面沿用正式版 demo：左侧“需要你决定”和“最近变化”，中间按阶段 × 工作线的关系图，右侧完整笔记。只读。

## 6. Skill 行为（`SKILL.md`）

**触发描述**：当项目里存在 `.omino/`，或用户谈到项目目标、需求、安排、进展、以后再做的想法时使用。

**每轮流程：**

1. **判断**：这一轮是新的意图、安排变化、实际进展，还是只是提问、讨论、假设？只有前三类会改计划。
2. **读取**：先读 `project.md` 和当前阶段，再沿本轮涉及的笔记读相关的 `requires`、`refs` 和召回约定；不每轮全量读。会话开始时先跑一次 `check --fix` 和 `review`。
3. **写入或保持**：只改受影响的笔记，保留原因和来源；没有变化就什么都不写。改完调用 `record`。
4. **召回**：写入后跑 `recall`。条件成立就在回复里把想法带回讨论，然后 `--mark-fired`；不得把召回当成采纳。
5. **复核**：需求或约束变了，跑 `review`，告诉用户哪些结论需要重新确认、为什么。

**硬规则（写进 SKILL.md）：**

- 讨论、提问、假设不等于决定；拿不准时先问，不写。
- 列举顺序不等于执行前置；“先做 A”写成 `before`，不写成 `requires`。
- 新需求不一定新建阶段；用户没说就不开新阶段。
- 阶段结束不自动进入下一阶段；召回不自动采纳。
- 用户最新的暂缓或取消决定优先于旧的召回约定。
- agent 自己说“做完了”只能记为 `source: agent`；`verified` 必须有工具结果。
- 发现安排与 `project.md` 的边界冲突时，写 `review` 标记并告诉用户，不静默删除，也不继续推进。

`references/` 三份：`semantics.md`（概念与判断边界）、`format.md`（第 4 节的完整版）、`examples.md`（七轮推演逐轮的输入、期望动作和期望文件变化）。
