# Omino 项目框架

2026-11-17 定稿。这是 Omino 的整体定位和结构；各版本的实现细节见 `docs/dev/v0.md`。

## 定位

Omino 是给 agent 写、给人读的项目记忆：一种放在仓库里的 Markdown 格式，加一套 skill。它记的是项目**定下了什么**、为什么、在等什么，而不是过程里发生了什么。用得越久、笔记之间连得越多，价值越大。

| 产品 | 记什么 | 谁来写 | 放在哪 | 和 Omino 的关系 |
| --- | --- | --- | --- | --- |
| claude-mem | 发生了什么（每次工具调用） | 自动记录 | 本机数据库 | 可以并存：它是原始日志，Omino 是整理后的结论 |
| Obsidian | 人的笔记 | 人 | 本地 Markdown | 借鉴：纯文件、笔记互相链接；`.omino/` 应能直接当 Obsidian 库打开 |
| Linear | 谁在做什么 | 团队成员和 agent | 云端 | 不重叠：负责人、优先级、迭代这些留给它 |
| OpenSpec | 一次变更怎么做 | agent | 仓库 | 互补：Omino 的工作项可以链接到某个 OpenSpec 变更 |

一句话：**claude-mem 记住发生了什么，Omino 记住定下了什么。**

## 核心原则

1. **本机的计划目录是唯一的数据源。**计划放在 `~/.omino/projects/<id>/`，同一个项目的所有 worktree 和 clone 共用一份；目录本身是 git 仓库，每次记录提交一次，有完整历史。没有服务器副本，没有数据库。（v0.5 起；之前放在仓库里的 `.omino/`，并行 worktree 会互相冲突。）
2. **每个改动都有来源。**agent 按规则改计划并记下用户原话；用户也可以在页面上直接改笔记、确认待确认的事，改动当场记作用户的（`via: page`）；页面上的回答、质疑和留言写进笔记的 `## Comments`，由 agent 照着做完再删掉。（v0.6 起；之前页面只能把“提议”送进 inbox。）
3. **讨论不等于决定，想起不等于采纳。**agent 起草的内容标着“待确认”，用户确认后才算数。
4. **价值来自关系和积累。**新建笔记前先找能挂靠的旧笔记；孤立的笔记要提示。
5. **不打扰。**计划没变就不提；hook 只在会话开始、每次发消息、每轮结束这三处运行，不调用模型，几十毫秒内结束。
6. **不依赖任何服务或产品。**不用账号也能完整使用；Mandala 可以用 Omino，但 Omino 离开 Mandala 仍然完整。

## 组成部分

| 部分 | 作用 |
| --- | --- |
| 计划目录格式 | 意图、阶段、工作、想法、决定五类笔记，加变化记录；用户的留言在笔记的 `## Comments` 里；格式版本号在 `state.json` |
| skill | 规则：什么时候记、怎么判断、什么要用户确认 |
| 命令行 `omino` | `init`、`record`、`check`、`find`、`brief`、`recall`、`review`、`view`、`service`、`hook`、`hooks`、`doctor` 等 |
| 页面服务 | 本机一个常驻的小服务，固定端口 4870，`/p/<id>` 是每份计划的页面：关系图、看板、列表、历史；可以编辑笔记、确认、留言。hook 启动它，可选开机自启；服务不在时 `view.html` 只读 |
| hook | 会话开始给简报并启动页面服务；发消息时带入页面上的新留言和修改；每轮结束提醒记录 |

格式版本：命令行遇到比自己新的格式就拒绝写入并提示更新；遇到旧格式则提示迁移，迁移在仓库里产生普通的 git 改动。同一个大版本内只加字段、不删字段，旧版本忽略不认识的字段。

## 发布、安装与更新

| 形态 | 给谁 | 怎么装 | 怎么更新 | hook 怎么来 |
| --- | --- | --- | --- | --- |
| Claude Code 插件 | Claude Code 用户 | `/plugin marketplace add maktub-ai/omino`，再 `/plugin install omino@omino` | `/plugin update omino` | 插件自带 `hooks/hooks.json` |
| 通用 skill | Codex 等其他 agent | 把 `skills/omino` 复制到对应 agent 的 skills 目录（v0.5 起提供 `npx` 安装） | 重新复制或安装 | 第一次使用时运行 `omino doctor`，缺什么就问用户，同意后再装；装不了就在 AGENTS.md 里加一行提示 |
| Mandala 插件 | Mandala 用户 | Mandala 应用市场，可选安装 | 随 Mandala 市场 | 由 Mandala 提供等价能力 |

- 不悄悄安装：写用户的配置文件、在仓库里加文件或把计划目录写进 agent 配置之前，都要先说清楚并得到同意。
- 命令行随 skill 一起分发，零依赖。
- 同一台电脑上可能有几个版本；格式版本号保证旧版只会拒绝写入，不会把文件写坏。

## 日常如何运转

1. **会话开始**（SessionStart）：`omino brief` 给 agent 十行左右的简报（含待处理的留言和页面链接），页面服务没在运行就启动它。
2. **用户每次发消息**（UserPromptSubmit）：用户在页面上新留的言、新做的修改，带进上下文。
3. **agent 干活**：用户定了事、方向变了、工作完成了，就改笔记并 `record`（带用户原话和会话 id），在回复里列出改了哪几篇、附链接。新建笔记前先 `find`。
4. **每轮结束**（Stop）：这一轮改了文件却没有记录时，提醒 agent 一次；只提醒、不拦截。纯对话里的决定靠 skill 规则记录。
5. **会话结束**：什么都不用做。页面服务不属于任何会话，一直在；页面上的留言等下一次会话处理。

## 一份计划管什么：情况分类

计划是一条有目标的工作主线，不等于一个仓库。目录只是这条主线落在哪里。

| # | 情况 | 例子 | 计划代表什么 | 和目录的关系 | 泳道 / 阶段 | 关联记在哪 |
|---|---|---|---|---|---|---|
| 1 | 单仓库的独立项目 | 个人工具、小 App | 这个产品 | 1 个仓库 ↔ 1 份计划 | 泳道是模块，阶段是版本 | 提交 `.omino.json` |
| 2 | 多仓库的产品 | Mandala：App + 官方服务 + 网站 | 这个产品 | 多个仓库 → 1 份计划（`link`） | 泳道是服务或仓库（`lane`），阶段是推进步骤，跨服务用依赖 | 各仓库提交 |
| 3 | monorepo 多个包 | `apps/web` + `apps/api` | 同一目标就一份，否则各一份 | 1 个仓库 → 1 份或多份 | 一份时泳道是包 | 子目录各放 `.omino.json` |
| 4 | 团队大仓库里自己负责的一件事 | billing-service 里的发票导出 | 这件事 | 1 个仓库 → 先后多份计划 | 阶段是这件事的步骤；做完 `close`，下一件 `init --name` | 只记在本机 |
| 5 | 团队共享的计划 | 小组一起维护的产品 | 这个产品 | 同 1、2 | 泳道可以是负责人或服务 | 提交，并需要同步（v0.6） |
| 6 | fork / 给开源项目贡献 | 改一个开源编辑器 | 你要改出什么 | 1 个 fork ↔ 1 份计划 | 上游现状放「Before Omino」，提给上游的 PR 是工作项 | 只记在本机，绝不进 PR |
| 7 | 一个工作区包含多个目录 | Codex project、多目录工作区 | 通常是一个产品 | 父目录或每个仓库 → 1 份计划 | 同 2 | 父目录 `.omino.json`，或各仓库 `link` |
| 8 | 非代码的工作 | 调研、写作、学习 | 这件事 | 1 个文件夹 ↔ 1 份计划 | 阶段是步骤，泳道是主题 | 文件夹里的 `.omino.json` |
| 9 | 一个人管很多份计划 | 同时推进多个产品 | — | — | — | `omino projects --open` 总览 |
| 10 | 临时的一次性任务 | 修一个 bug | 不需要计划 | — | — | — |

划分规则：
- **目标相同就是同一份计划。**能独立完成、独立复盘的事才单独开一份。
- **并行的部分放泳道**（服务、仓库、模块、负责人），**先后的部分放阶段**（版本、推进步骤）。
- **拆成新计划只有三种原因：**目标不同；归属不同（个人计划不混进团队计划）；上一份已经结束。
- **关联要不要提交看仓库是谁的：**自己的仓库提交 `.omino.json`；团队仓库和 fork 默认只记在本机，第一次问一句。
- **目标怎么写：**写这份计划要达成什么、边界、为什么，不写「这个仓库是什么」。老仓库和 fork 的背景放在「Before Omino」和依据里。

## 线上与远程

不在 Omino 开源项目里做。以后作为 Mandala 远程连接的一部分：服务器只转发、不保存计划；电脑离线时暂存提议、送达即删；线上只能读计划、加想法、回答问题、提议决定，执行层面的事实只在电脑上发生。多台电脑之间的同步放到 v0.6：同步单位是 `changes.jsonl` 里只追加的事件，先支持 git remote，再支持一个最小的自部署服务端。

## 不做的事

- 负责人、优先级、估时、截止日期、迭代、通知、评论串、多人权限。
- 在服务器上存计划，或者两边都能改的双向同步。
- 每次工具调用都自动记一笔。
- 在 hook 里调用模型，或者常驻后台进程（等做远程连接时再说）。
- 暂不做桌面 app：Mandala 就是那个 app。
