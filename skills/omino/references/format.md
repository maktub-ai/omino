# File format

Plans live outside the project: `~/.omino/projects/<id>/` (`OMINO_HOME` overrides `~/.omino`). Every worktree and clone of a project on one machine shares that folder.

Three links, each in one place:

| Link | Kept in | Says |
|---|---|---|
| project → plan id | the repository's `.git` (`omino-project`, this machine only); or `.omino.json` in the project folder, committed, when the user shares it (`--share`) | which plan this project uses |
| plan id → folder | `~/.omino/projects/<id>/` | where the plan is on this machine |
| plan → repositories | `omino.json` in the plan folder (its history) | `repos` (normalized remotes; a folder's path when it has none), `lanes` (remote or `path:` → lane name), `status` (`active` / `closed`, `closedAt`) |

The id of a folder is the nearest `.omino.json` (walking up to the git root, so a monorepo package can have its own plan), else, at a worktree root, the file `omino-project` in the git common directory (written by `init` and `link`; it covers worktrees made before `.omino.json` was committed). An invalid `.omino.json` is an error, never a fallback. A new id is `owner-repo` from the origin remote (plus the package path in a monorepo), so other clones attach to the same plan; without a remote it is the folder name, made unique.

When a folder's remotes are not among the plan's `repos` (a fork, a renamed remote, a copied `.omino.json`), the brief, `where` and `doctor` say so and the agent asks before changing the plan; `omino link <id>` confirms and adds the remote. Several repositories can share one plan by linking to the same id. `.paths.json` (not in history) remembers the folders on this machine that used the plan; `omino projects` lists them. Every `--json` answer starts with `project: {id, via, root}`.

`~/.omino/offered.json` lists the projects without a plan where Omino already asked the user once whether to keep one; it never asks there again.

The plan folder is its own git repository: `init`, `migrate` and every `record` add a commit there. Its `.gitignore` keeps the per-machine files below out of that history.

```
~/.omino/projects/<id>/
├── project.md        # kind: intent, id: project
├── stages/<id>.md
├── work/<id>.md
├── ideas/<id>.md
├── decisions/<id>.md
├── changes.jsonl     # append-only history, written by `record`
├── .hooks.json       # what the hooks already told each session (not in history)
├── state.json        # format version and last recorded fingerprint of each note, written by `record`
├── .lock/            # held while a command changes the plan, so two agents never write at once (not in history)
├── view.html         # generated by `view` (not in history)
└── summary.json      # written with view.html: title, stage progress, what waits for the user, for other apps (not in history)
```

Links from a note to a project file start with `/` and are relative to the project folder: `[api](/src/api.ts)`. Links that climb out of the plan folder (`../src/api.ts`, written when plans lived in `.omino/`) still resolve against the project folder.

Omino 0.4 and earlier kept this folder as `.omino/` inside the project; `omino migrate` copies it to the shared folder. Omino 0.5 kept `inbox.jsonl`, `.serve.json` and `.live.json` here for its per-plan page server; the hooks turn answers still waiting in `inbox.jsonl` into comments (below) and keep the file as `inbox.migrated.jsonl`.

The page service, one per machine, keeps `~/.omino/server.json` (its port, token, process and version, while it runs) and `~/.omino/token` (the token it accepts on `/api/`, the same across restarts). Pages are at `http://127.0.0.1:4870/p/<id>` (`OMINO_PORT` changes the port; another one is taken only when it is busy). Other apps that show a plan (a Mandala tab) read the token from `server.json` and send it as `x-omino-token`: `GET /api/plans`, `GET /api/plans/<id>/summary`, `GET /api/plans/<id>/events` (server-sent `changed`), `GET`/`PUT /api/plans/<id>/notes/<note>` (`{text, base}`; 409 when the note changed since `base`), `POST /api/plans/<id>/notes/<note>/comment` (`{text, label}`) and `…/confirm` (`{about}`).

## Format version

`state.json` carries `"version"`, the file format (currently 1). A copy of Omino that meets a newer format refuses to change the plan and asks to be updated; within one format version, new fields are only ever added, and older copies ignore fields they do not know.

## Frontmatter subset

Every note starts with frontmatter between two `---` lines. Only this subset is accepted:

- one `key: value` per line, keys in `lower_snake_case`
- values: plain text, integers, or inline lists `[a, b, c]`
- no nesting, no multi-line values (`|`, `>`), no comments, no duplicate keys

## Fields

| Field | Kinds | Required | Notes |
|---|---|---|---|
| `id` | all | yes | `[a-z0-9-]+`, unique, equal to the file name without `.md` |
| `kind` | all | yes | `intent`, `stage`, `work`, `idea`, `decision`; must match the folder |
| `title` | all | yes | one line |
| `level` | stage | yes | integer: 1, 2, 3 …; `0` is reserved for the "Before Omino" summary stage of an adopted project |
| `status` | stage | yes | `planned`, `active`, `closed` |
| `stage` | work | yes | id of a stage note |
| `status` | work | yes | `planned`, `doing`, `done`, `verified`, `dropped` |
| `source` | stage, work | no | `user`, `agent`, `tool`, `file` — who reported the current status |
| `lane` | work | no | workstream name, free text; groups items into rows |
| `order` | work | no | integer; display order within a stage |
| `requires` | work | no | list of work ids that must be done first |
| `before` | work | no | list of work ids this should come before (preference only) |
| `refs` | work, idea | no | list of any note ids for context |
| `parent` | work | no | id of the work item this one is part of |
| `branch` | work | no | git branch (or worktree branch) where it is being implemented |
| `date` | decision | yes | `YYYY-MM-DD` |
| `supersedes` | decision | no | ids of stages, work, ideas or decisions this decision replaces; they are shown as superseded |
| `affects` | decision | no | ids that may need another look (`project` for a decision about the whole project); `record` flags the ones already under way |
| `idea_state` | idea | yes | `open`, `deferred`, `adopted`, `dropped` |
| `recall` | idea | no | `stage <id> closed`, `work <id> done`, or `manual <text>` |
| `recall_state` | idea | with `recall` | `waiting`, `fired`, `stopped` |
| `review` | any | no | one-line reason the item needs the user's re-confirmation |
| `basis` | work | written by CLI | completion fingerprint; never edit by hand |

Unknown fields produce a warning and are ignored.

## Body

Use English `##` headings so tools can find sections; write the content in the project's language.

| Section | Used for |
|---|---|
| `Purpose`, `Principles`, `Boundaries` | `project.md` |
| `Why` | The reason this item exists |
| `Requirements` | What "done" means. Completion is fingerprinted against this section. |
| `Arrangement` | Why it sits where it sits, ordering preferences |
| `Progress` | What happened, in prose, with who reported it |
| `Idea`, `Recall`, `Decision` | For ideas |
| `Before`, `Now`, `Why`, `Given up` | For decisions |
| `Open questions` | Any note: one bullet per question only the user can settle. Each bullet appears under "needs your decision" until removed. |
| `Comments` | Any note: what the user asks of the agent, one block each, until the agent has dealt with it and removed it (see below). |

A comment is a quote block whose first line starts with `[!omino]`, optionally followed by a short label; the lines after it are the user's words:

```
## Comments

> [!omino] Answer to "Which list first?"
> Inbox first.
```

The page writes them; a person can also type one in any editor. They live in their own section so they never change `Requirements` (and never make finished work look out of date).

Other headings are fine.

## changes.jsonl

One JSON object per line, appended by `record`:

```json
{"ts":"2026-11-15T09:00:00Z","source":"user","summary":"Add filter before delete; still stage 1","said":"Add a filter for open items. Do that first, delete later.","notes":[{"id":"filter","op":"created"},{"id":"del","op":"modified"}]}
```

Entries may also carry `session` (from `--session` or the `OMINO_SESSION` environment variable) and `git` (`branch`, `commit`, and `worktree` for linked worktrees), captured automatically. Changes the user made on the page carry `"via":"page"` and `page` (`edit`, `comment` or `confirm`) instead of `git`, and list only the notes they changed.

`op` is `created`, `modified` or `deleted`. `said` (optional) quotes the user's words that led to the change, so each entry can be traced back to a moment in a conversation.
